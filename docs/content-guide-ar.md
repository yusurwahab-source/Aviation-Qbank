## 0. الصورة الكبيرة في دقيقة واحدة

الموقع = **أسئلة اختيار من متعدد** مخزّنة كملفات نصية (JSON) داخل مجلد اسمه `content/`.

```
ملفات الأسئلة (JSON)  →  npm run db:seed  →  قاعدة البيانات  →  الموقع يعرضها للطالب
   (أنت تكتبها)         (يعمل تلقائياً عند النشر)
```

**القاعدة الذهبية:** الملفات هي "الحقيقة". لا تعدّل الأسئلة داخل قاعدة البيانات أبداً — أول نشر قادم سيمسح تعديلك ويعيد ما في الملفات.

**القاعدة الثانية:** أي دفع (push) إلى فرع `main` = **نشر مباشر للموقع الحي** (يشغّل migration + seed على قاعدة البيانات الحية ثم يبني الموقع). لذلك نعمل دائماً بهذا الترتيب: فرع جديد ← Pull Request ← انتظر CI أخضر ← ادمج.

## 1. الفلسفة (لماذا الملفات مبنية هكذا؟)

1. **الهدف الفهم لا الحفظ.** كل خيار خاطئ يجب أن يُستبعد بمعرفة النظام، لا بشكل الجملة. سؤال لا يُجاب إلا إذا رأيته قبل ذلك = خطأ في المحتوى وليس محتوى.
2. **إضافة طائرة أو مادة = إضافة مجلد فقط.** لا يُعدَّل أي كود. إذا احتاج الأمر تعديل كود لإضافة طائرة جديدة فهذا دليل على أنك تفعله بطريقة خاطئة. (استثناءات صغيرة جداً مذكورة في الوصفات.)
3. **ثلاث شجرات محتوى منفصلة** (وليس جدول واحد): Type Rating، Class Rating، Flying Knowledge (ATPL). تتشابه في الشكل لكن كل واحدة لها جداولها ومخططها.
4. **الفشل بصوت عالٍ.** أي خطأ في ملف أسئلة يوقف البناء ويطبع اسم الملف والحقل والمشكلة. لا يمكن لسؤال معطوب أن يصل للطالب.
5. **التاريخ لا يُمسّ.** إجابات الطلاب تُحفظ بدون ارتباط (foreign key) بجدول الأسئلة. لذلك حذف أو تعديل سؤال لا يمسح تاريخ أحد، ولا يتعطل بسببه النشر. **ولهذا: لا تعِد استعمال رقم سؤال (id) قديم أبداً.**
6. **الكود الرمزي للطائرة/المادة (مثل `DA40`, `POF`) لا يتغيّر بعد النشر.** هو جزء من الرابط، وبادئة كل id، ومخزّن في كل إجابة. يمكن تغيير الاسم الظاهر (`name`) لكن لا يمكن تغيير الكود إلا بعملية ترحيل (migration).
7. **المحتوى الأكاديمي (ATPL) لا يذكر أي مصدر للطالب.** لا اسم كتاب ولا مدرسة ولا جهة تنظيمية ولا "بنك أسئلة" في السؤال أو الخيارات أو الشرح أو التاجز أو دليل الدراسة. المصادر تُسجَّل فقط في `content/README.md` و`CLAUDE.md`.

## 3. رحلة السؤال: من ملف إلى شاشة الطالب

1. تكتب السؤال في ملف `.json` داخل `content/.../questions/`.
2. `npm run validate:content` يفحص كل ملف حسب المخطط (يعمل تلقائياً قبل أي build/seed).
3. `npm run db:seed` يزامن قاعدة البيانات مع الملفات: **يضيف** الجديد، **يحدّث** الموجود (حسب id)، **ويحذف** ما اختفى ملفه.
4. الموقع يقرأ من قاعدة البيانات، ويعرض فقط الأسئلة ذات `"status": "published"`.
5. الصفحة نفسها لا تحتوي الإجابة الصحيحة أبداً؛ تصل الإجابة والشرح فقط كردّ على إجابة الطالب، سؤالاً سؤالاً.

**ماذا يعني هذا عملياً لك:** لا تحتاج لمس أي صفحة لتظهر أسئلتك. العدّادات في الصفحة الرئيسية، قائمة المواضيع، الـ sitemap — كلها تُحسب تلقائياً من المحتوى.

## 4. شكل السؤال (الحقول وقواعدها)

| الحقل | مطلوب؟ | القاعدة |
|---|---|---|
| `id` | ✅ | `الكود-رمزالموضوع-4أرقام` مثل `POF-AERO-0001`. فريد. البادئة = كود الطائرة/المادة. رمز الموضوع 2–8 أحرف كبيرة/أرقام |
| `aircraft` **أو** `classCode` **أو** `subjectCode` | ✅ | حسب الشجرة (انظر الجدول أدناه). يجب أن يطابق مجلد الطائرة/المادة |
| `topic` | ✅ | اسم الموضوع (حتى 60 حرفاً). **يجب أن يُكتب بنفس الإملاء حرفياً في كل أسئلته** — التقارير تجمع بالنص |
| `subtopic` | ❌ | موضوع فرعي (حتى 60 حرفاً) |
| `question` | ✅ | نص السؤال |
| `options` | ✅ | من 2 إلى 5 خيارات `{ "id": "a", "text": "..." }`. المعتاد 4. الـ id حرف صغير أو رقم (حتى 4). النص حتى 500 حرف |
| `correct` | ✅ | `id` الخيار الصحيح، ويجب أن يكون موجوداً فعلاً في `options` |
| `explanation` | ✅ | لماذا هذه الإجابة صحيحة (1–3 جمل). تظهر للطالب |
| `reference` | ❌ | المصدر (حتى 200 حرف) مثل `AFM 7.9.5`. مطلوب عملياً لبنوك الطائرات |
| `tags` | ❌ | كلمات قصيرة (حتى 20، كل واحدة حتى 40 حرفاً) |
| `media` | ❌ | محجوز للمستقبل — لا تستعمله الآن |
| `status` | ✅ | `draft` (لا يراه الطالب) أو `published` (يراه) |
| `version` | ✅ | رقم صحيح يبدأ بـ 1. **زِده بمقدار 1 كلما عدّلت السؤال** |

> ⚠️ أي حقل غير مذكور = خطأ (مثلاً `explaination`). هذا مقصود: يفشل البناء بدل أن يضيع الشرح بصمت.

### أي حقل لأي شجرة؟

| الشجرة | ملف التعريف | حقل الربط داخل السؤال |
|---|---|---|
| Type Rating | `content/<code>/aircraft.json` | `"aircraft": "B737"` |
| Class Rating | `content/classes/<code>/class.json` | `"classCode": "DA40"` |
| ATPL | `content/flying-knowledge/<code>/subject.json` | `"subjectCode": "POF"` |

### مثال كامل — سؤال ATPL (يوضع في ملف داخل `content/flying-knowledge/pof/questions/`)

الملف دائماً **مصفوفة** `[ ... ]` حتى لو فيه سؤال واحد. (المثال توضيحي: الرقم `0101` مجرد مثال — استعمل دائماً رقماً لم يُستعمل من قبل في المادة.)

```json
[
  {
    "id": "POF-AERO-0101",
    "subjectCode": "POF",
    "topic": "Basic Aerodynamics",
    "subtopic": "Lift",
    "question": "If the true airspeed doubles at constant air density and wing area, lift at a constant angle of attack:",
    "options": [
      { "id": "a", "text": "Doubles" },
      { "id": "b", "text": "Halves" },
      { "id": "c", "text": "Quadruples" },
      { "id": "d", "text": "Increases by about 41%" }
    ],
    "correct": "c",
    "explanation": "Lift is proportional to the square of airspeed, so doubling the speed multiplies lift by four.",
    "tags": ["lift", "airspeed"],
    "status": "published",
    "version": 1
  }
]
```

### مثال — سؤال طائرة Class Rating (`content/classes/da40/questions/`)

```json
{
  "id": "DA40-ELEC-0027",
  "classCode": "DA40",
  "topic": "Electrical",
  "question": "…",
  "options": [ { "id": "a", "text": "…" }, { "id": "b", "text": "…" }, { "id": "c", "text": "…" }, { "id": "d", "text": "…" } ],
  "correct": "b",
  "explanation": "…",
  "reference": "AFM 7.9.3",
  "status": "published",
  "version": 1
}
```

(وبنفس الشكل لـ Type Rating لكن بحقل `"aircraft": "B737"`.)

## 5. قواعد جودة السؤال (استخرجتها من الملفات ومن الـ prompt المحفوظ)

هذه ليست مفروضة آلياً، لكنها المعيار الذي اعتمدته أنت في بنوك ATPL:

1. **توزيع الإجابة الصحيحة:** كل حرف (a/b/c/d) بين **22% و28%** من أسئلة المادة. لا تجعلها دائماً `a`.
2. **طول الخيار:** الخيار الصحيح **ليس الأطول** في ثلثي الأسئلة على الأقل (المستهدف: الأطول صحيح ≤ 35%). اكتب المشتتات بطول قريب من الصحيح.
3. **كل مشتّت = خطأ شائع حقيقي** عند الطلاب. لا خيارات سخيفة، ولا "كل ما سبق"/"لا شيء مما سبق"، ولا خيار يكرر نص السؤال.
4. **خيار واحد فقط يمكن الدفاع عنه** من المادة نفسها.
5. **نوّع أنواع الأسئلة**، لا تجعلها كلها "أي مما يلي صحيح/خطأ".
6. **الأرقام:** كل الخيارات بنفس الصيغة والوحدة، والمشتتات أخطاء حساب معقولة. **احسب** ولا تعتمد على الذاكرة.
7. **معلومة غير مؤكدة؟** اجعلها `"status": "draft"` وأخبر المراجع.
8. **لا مصادر في نص الطالب** (ATPL): لا كتب ولا مدارس ولا هيئات.
9. **بنوك الطائرات:** كل سؤال له `reference` للقسم في الدليل الرسمي، ولا تنسخ من وثائق محمية بحقوق النشر.

> النص الكامل للـ prompt الذي تستعمله لكتابة مادة ATPL جديدة موجود في ملف المشروع `claude/question-authoring-prompt.md`.

## 6. الأوامر التي ستحتاجها

أول مرة بعد تنزيل المشروع:

```bash
npm install

npm run setup                    # migrate + seed
npm run dev                      # الموقع على http://localhost:3000
```

| الأمر | وظيفته |
|---|---|
| `npm run validate:content` | **أهم أمر لك.** يفحص كل ملفات الأسئلة ويخبرك بالخطأ بدقة |
| `npm run db:seed` | يحمّل المحتوى في قاعدة البيانات المحلية |

| `npm run dev` | تشغيل الموقع محلياً |

## 7. الوصفات (خطوة بخطوة)

> قبل أي وصفة: أنشئ **فرعاً جديداً** (مثلاً `add-nav-subject`). لا تعمل مباشرة على `main`.

### الوصفة A — إضافة أسئلة جديدة إلى موضوع موجود

مثال: إضافة 10 أسئلة إلى موضوع Stalling في POF.

1. افتح الملف: `content/flying-knowledge/pof/questions/stalling.json`.
2. انزل لآخر سؤال واحفظ رقم id الأخير (مثلاً `POF-STALL-0087`).
3. أضف أسئلتك **بعد آخر عنصر** مع **فاصلة** بين العناصر، وقبل `]` النهائية. الأرقام تكمل من حيث توقف الرقم: `0088`, `0089`, …
4. تأكد أن `topic` مطابق حرفياً لما في الأسئلة الأخرى بالملف (نفس الإملاء، نفس المسافات).
5. ابدأ بـ `"status": "draft"` إن لم تكن متأكداً، و`"version": 1`.
6. شغّل:
   ```bash
   npm run validate:content
   ```
   يجب أن ترى `Content is valid`. وإلا اقرأ اسم الملف والحقل في الرسالة.
7. تحقق من توزيع الحروف وطول الخيارات (القسم 5).
8. غيّر `draft` إلى `published` للأسئلة المراجعة.
9. انشر (القسم 8).

### الوصفة B — إضافة **موضوع جديد** (Topic) داخل مادة/طائرة موجودة

"الموضوع" هو ما يسميه الطالب "Section/Chapter" داخل المادة (مثل Stalling أو Electrical).

1. أنشئ ملفاً جديداً في مجلد `questions/` للمادة، باسم بحروف صغيرة وشرطات، مثل `wake-turbulence.json`. **اسم الملف لا يهم للموقع** (يقرأ كل ملف `.json`) لكنه يُسهّل عليك الأمر.
2. اكتب فيه مصفوفة أسئلة، كلها بنفس قيمة `topic` الجديدة، مثل `"topic": "Wake Turbulence"`.
3. اختر **رمز موضوع** (2–8 أحرف كبيرة) ليدخل في الـ id: `POF-WAKE-0001`, `POF-WAKE-0002` …
4. لا تعدّل أي كود: الموضوع الجديد يظهر **تلقائياً** في منشئ الاختبار بعدد أسئلته.
5. ملاحظة: قائمة المواضيع في الموقع تُرتَّب **أبجدياً بالاسم**، وليس بترتيب الملفات.
6. `npm run validate:content` ثم انشر.
7. حدّث جدول الملفات في `content/README.md` (اسم الملف، الموضوع، عدد الأسئلة).

### الوصفة C — إضافة **مادة ATPL جديدة** (مثل General Navigation)

الأقرب لـ "content only" مع تعديلين صغيرين بالكود.

**1) أنشئ المجلد** (الكود 2–8 أحرف كبيرة، والمجلد بحروف صغيرة):
```
content/flying-knowledge/nav/
   subject.json
   questions/
      <topic-1>.json
      <topic-2>.json
```

**2) اكتب `subject.json`:**
```json
{
  "code": "NAV",
  "name": "General Navigation",
  "description": "وصف المادة بالإنجليزية (حتى 600 حرف).",
  "status": "active",
  "sortOrder": 60
}
```
- `status: "active"` **يتطلب** وجود ملف أسئلة واحد على الأقل، وإلا يفشل التحقق.
- `sortOrder`: رقم 0–9999 يحدد ترتيب العرض.

**3) اكتب الأسئلة** بالـ prompt المحفوظ (انظر القسم 5). كل سؤال: `"subjectCode": "NAV"` والـ id يبدأ بـ `NAV-`.

**4) سجّل المادة في قائمة ATPL** — ملف `src/lib/atpl-subjects.ts`:
هناك صف جاهز لكل مادة. أضف `code` للصف الموجود، مثلاً:
```ts
{ number: "061", name: "General Navigation", code: "NAV" },
```
بدون هذا السطر يبقى الصف "قريباً" ولا يربط بالمادة الحية.

**5) (موصى به) دليل الدراسة:**
- أنشئ `public/nav-study-guide.html` (اتخذ `public/pof-study-guide.html` نموذجاً).
- أضف الكود في `src/lib/study-guide.ts` داخل المجموعة:
  ```ts
  const STUDY_GUIDE_CODES = new Set(["DA40", "C152", "DA42", "A320", "POF", "HPL", "COM", "MET", "NAV"]);
  ```
  (السبب: على Vercel لا يمكن للكود التحقق من وجود الملف، فالقائمة تُحفظ يدوياً.)

**6)** `npm run validate:content` ثم `npm run check` ثم انشر.

**7)** سجّل في `content/README.md` ملاحظة عن البنك (عدد الأسئلة، أنها مكتوبة بالمساعد، وأنها تحتاج مراجعة مدرّب).

> المادة ATPL **مجانية بالكامل** بقرار منك: لا يحسبها عدّاد الأسئلة المجانية ولا الاشتراك.

### الوصفة D — إضافة **طائرة Type Rating** جديدة (طائرة كبيرة)

```
content/e190/
   aircraft.json
   questions/
      electrical.json
      hydraulics.json
```

`aircraft.json`:
```json
{
  "code": "E190",
  "name": "Embraer E190",
  "manufacturer": "Embraer",
  "variant": "E190 (اختياري)",
  "description": "وصف قصير حتى 600 حرف.",
  "status": "active",
  "sortOrder": 40
}
```
- الأسئلة: `"aircraft": "E190"` و id مثل `E190-ELEC-0001`.
- لا كود يتغير. تظهر الطائرة تلقائياً في `/type-rating`، وفي الـ sitemap، وعدّادات الصفحة الرئيسية.
- **دليل الدراسة (اختياري):** `public/e190-study-guide.html` + إضافة `"E190"` في `STUDY_GUIDE_CODES`.
- **تذكير:** بنك الـ A320 بُني من وثائق عامة، وكل نصوصه تقول للطالب "للدراسة فقط وتحقق من FCOM المشغّل". افعل المثل لأي طائرة لا تملك مصدراً رسمياً.
- يمكنك وضع `"status": "coming_soon"` لعرض الطائرة قبل جاهزية البنك (لن يكون لها رابط في sitemap).

### الوصفة E — إضافة **طائرة Class Rating** جديدة (طائرة خفيفة)

نفس الوصفة D لكن:
```
content/classes/pa28/
   class.json          ← (وليس aircraft.json)
   questions/...
```
`class.json` ليس فيه `manufacturer` ولا `variant`:
```json
{
  "code": "PA28",
  "name": "Piper PA-28 Cherokee",
  "description": "…",
  "status": "active",
  "sortOrder": 30
}
```
والأسئلة: `"classCode": "PA28"` و id مثل `PA28-FUEL-0001`.
**لا يوجد تقسيم "single engine/multi engine"** — الطائرة الخفيفة تحت Class Rating مباشرة (DA42 ثنائية المحرك موضوعة هناك أيضاً).

### الوصفة F — إضافة **محاكي** جديد إلى Pilot Sims

المحاكي صفحة HTML مستقلة. **لا تعدّل داخل ملفاته من هذا المشروع** — إذا احتاج تعديلاً فهو ملف جديد منك.

1. ضع الملف: `public/pilot-sims/my-sim.html`.
2. في `src/app/pilot-sims/sims.ts` أضف عنصراً **داخل** المصفوفة `PILOT_SIMS` (قبل `];` مباشرة):
   ```ts
   {
     slug: "my-sim",
     name: "My Simulator",
     description: "وصف قصير يظهر في بطاقة القائمة.",
     file: "/pilot-sims/my-sim.html",
     tier: "free",
   },
   ```
3. أنشئ صفحة: `src/app/pilot-sims/my-sim/page.tsx` — انسخ `src/app/pilot-sims/vor-ndb-trainer/page.tsx` وغيّر `findPilotSim("my-sim")` والعنوان.
4. أضف السطر في `src/lib/seo/sitemap-entries.ts` ضمن `STATIC_PAGES` (كما في المحاكيين الحاليين).
5. `npm run check` ثم انشر.

> ⚠️ **أخطر خطأ شائع:** لصق القالب *خارج* المصفوفة (بعد `}` الأخيرة للملف). هذا بالضبط ما حدث الآن في المستودع — انظر القسم 10.

### الوصفة G — إضافة **قسم جديد على مستوى الموقع** (غير موجود مثل "Air Law Trainer" أو شجرة رابعة)

هذه **ليست** عملية محتوى فقط. لو كان ما تريده:

| ما تريده | هل هو content-only؟ |
|---|---|
| مادة ATPL جديدة | ✅ نعم (الوصفة C) |
| طائرة جديدة | ✅ نعم (D أو E) |
| موضوع جديد داخل مادة/طائرة | ✅ نعم (B) |
| محاكي | ⚠️ ملف + 3 تعديلات صغيرة (F) |
| إخفاء/إعادة تسمية قسم أو طائرة | ✅ بدون كود: من `/owner/settings` |
| **شجرة محتوى رابعة** (نوع محتوى مختلف ليس سؤال اختيار من متعدد) | ❌ تحتاج كوداً: مخطط + loader + جداول + migration + استعلامات + صفحات |
| **ركيزة (Pillar) جديدة** على الصفحة الرئيسية | ❌ تحتاج كوداً (`src/lib/pillars.ts` والصفحة الرئيسية والهيدر) |

للحالتين الأخيرتين: اطلب من Claude Code، وأعطه هذه الجملة:

> "أريد إضافة قسم جديد اسمه X. اقرأ CLAUDE.md أولاً (خصوصاً أقسام: the three sections، pillars، Layout). اشرح لي الخطة بلغة بسيطة قبل التنفيذ، ثم ابنِه في فرع وPR واحد، مع اختبارات، ولا تلمس FREE_MODE."

### الوصفة H — تعديل أو حذف سؤال

- **تعديل:** عدّل النص في الملف **وزِد `version` بمقدار 1**. لا تغيّر الـ id.
- **حذف مؤقت:** غيّر `status` إلى `draft` (يختفي عن الطلاب ويبقى في الملف).
- **حذف نهائي:** احذف العنصر من الملف. بعد النشر يُحذف من قاعدة البيانات، **وتبقى إجابات الطلاب القديمة سليمة** (هذا مقصود). لا تعِد استعمال الـ id.

### الوصفة I — تغيير ما يظهر بدون نشر

من لوحة المالك `/owner/settings` (حساب `OWNER_EMAIL` فقط): إخفاء قسم أو طائرة أو مادة، إعادة تسمية قسم، تغيير اسم/وصف طائرة ظاهرين، عدد الأسئلة المجانية، شريط الإعلان، نسبة النجاح. هذا طبقة عرض فقط ولا يلمس المحتوى.

## 8. النشر (الآمن)

**الطريقة الموصى بها لك:** اطلب من Claude Code: "نفّذ الوصفة C لمادة NAV، ثم `npm run check`، ثم افتح PR". هو يتولى الفرع والـ PR، وأنت تراجع.

**ما يحدث عند الدمج في `main`:**
1. GitHub Actions (CI) يشغّل validate + lint + typecheck + test على قاعدة بيانات مؤقتة.
2. Vercel يشغّل `vercel-build`: **migrate ← seed (على قاعدة البيانات الحية) ← build**.
3. إذا فشل التحقق من المحتوى، **لا يصل شيء للقاعدة** ويبقى الموقع القديم يعمل.

**قاعدة المشروع عندك:** ادمج دائماً بعد أن يكون CI **أخضر**. لا تدمج وهو أحمر.

> إذا عدّلت ملف JSON من واجهة GitHub على الويب مباشرة، فاحرص أن تفعل ذلك في فرع جديد لا في `main`، لأن أي فاصلة ناقصة ستوقف التحقق.

## 9. الأخطاء الشائعة ومعناها

| الرسالة (تقريباً) | السبب | الحل |
|---|---|---|
| `Could not read or parse JSON` | فاصلة زائدة/ناقصة، أو اقتباس مفقود | ابحث قرب السطر؛ آخر عنصر في المصفوفة بدون فاصلة بعده |
| `Expected folder "da40"` / `Folder is "x" but the … code is "Y"` | اسم المجلد لا يطابق `code` (بحروف صغيرة) | سمِّ المجلد `code.toLowerCase()` |
| `Duplicate question id` | نفس الـ id مستعمل مرتين | غيّر الرقم؛ لا تعِد استعمال id قديم |
| `"correct" is "e" but the options are [a, b, c, d]` | `correct` لا يشير لخيار موجود | صحّح الحرف |
| `Question id starts with "X" but …` | بادئة الـ id لا تطابق كود الطائرة/المادة | صحّح البادئة |
| `Unrecognized key` | حقل غير مسموح أو خطأ إملائي (مثل `explaination`) | احذفه أو صحّح اسمه |
| `Question id must look like …` | صيغة الـ id خاطئة | `CODE-TOPIC-0001`: حروف كبيرة، رمز الموضوع 2–8، أربعة أرقام |
| `Subject X is "active" but has no question files` | `status: active` بدون ملفات أسئلة | أضف ملفاً، أو اجعلها `coming_soon` |
| `Question is in the X folder but declares subjectCode "Y"` | سؤال وُضع في مجلد مادة أخرى | انقله أو صحّح الحقل |
| `A question needs at least 2 options` / `at most 5` | عدد الخيارات | 2 إلى 5 |
| المادة لا تظهر "حية" في صفحة ATPL | لم تُضف `code` في `atpl-subjects.ts` أو لا أسئلة `published` | أضف السطر وتأكد من وجود أسئلة منشورة و`status: active` |
| رابط دليل الدراسة لا يظهر | الكود غير موجود في `STUDY_GUIDE_CODES` | أضفه |
